# OrbitFabric v1.2.0 - Core Integration Input Consolidation

Release date: 2026-08-28

## Summary

OrbitFabric v1.2.0 consolidates the production-facing Core Integration Input boundary designed and reference-proven after v1.1.0.

The release makes no changes to Mission Model semantics. It promotes selected Core-owned integration surfaces to stable compatibility commitments while preserving the narrow Mission Data Contract architecture and the existing v1 stable model.

The main release chain is:

```text
Mission Model
    -> OrbitFabric Core
    -> Mission Snapshot
       + Entity Index
       + Relationship Manifest
       + Lint Report
       + Model Summary
    -> coherent Core Integration Input Set
    -> external Integration Package / Adapter
```

## Stable additions

### Mission Snapshot

`mission_snapshot.json` is now a stable Core-owned inspection and integration surface for the complete loaded Mission Model and structured load diagnostics.

Its existing format identifier remains `0.1-candidate`. Stability classification is independent from the format-version token. Retaining the identifier avoids an artificial compatibility break.

The stable promise protects the documented envelope, boundary semantics and faithful serialization role. It does not freeze the complete `model` payload byte-for-byte. That payload follows Mission Model compatibility rules.

### Core Integration Input Set

`orbitfabric export integration-input-set` is now the stable Core-owned integration input workflow.

The coherent set preserves:

- one Core load/lint operation;
- required `mission_snapshot`, `entity_index`, `relationship_manifest` and `lint_report` roles;
- canonical `model_summary` companion role;
- per-surface identity, format version and SHA-256;
- RFC 8785/JCS input-set fingerprinting;
- explicit load, lint and surface failure states;
- manifest-last coherence;
- no raw-YAML semantic fallback.

Its `input_set_version` remains `0.1-candidate` for compatibility with the already reference-proven producer and consumer chain.

### Additive FDIR relationships

Seven explicit FDIR relationship families are admitted as additive stable-compatible extensions of `relationship_manifest.json`:

```text
autonomous_action_triggered_by_fault
autonomous_action_uses_command_source
fault_observes_telemetry
fault_recovery_dispatches_command
fault_recovery_targets_mode
recovery_intent_includes_command
recovery_intent_targets_mode
```

The original v1 Relationship Manifest golden remains unchanged. Dedicated tests protect the new additive families.

## Compatibility impact

### Mission Data Contract

No semantic change.

No Mission Model fields, controlled values, identifier rules, reference meanings or domain semantics are removed, renamed or redefined.

The stable Mission Model continues to cover spacecraft and subsystems, modes, telemetry, commands, events, faults, packets, policies, payloads, data products, contact/downlink assumptions and commandability/autonomy contracts.

### CLI

The documented Mission Snapshot and Integration Input Set export workflows are stable Core workflows from v1.2.0.

Existing stable commands remain compatible. Candidate v1.1 inspection commands remain candidate.

### JSON and Core-owned structured surfaces

Mission Snapshot and the coherent Integration Input Set receive stable compatibility classification. Their existing format identifiers remain unchanged.

The original stable `model_summary.json`, `entity_index.json`, lint report, simulation report and admitted Relationship Manifest families remain supported.

The v1.1.0 dashboard summary, scenario run index, coverage summary and structured simulation expectation additions remain candidate unless separately promoted.

### Lint and scenario evidence

No lint diagnostic policy or scenario evidence semantic change.

### Generated runtime and ground artifacts

No stability promotion or semantic change.

Generated C++17 runtime-facing bindings and generic ground-facing artifacts remain reproducible contract artifacts, not flight software or a ground segment.

## Extension contract posture

The broader Integration Framework is reference-proven, but v1.2.0 does not silently promote extension-owned contracts to stable Core surfaces.

The following remain independently versioned `0.1-candidate` extension contracts:

```text
Projection Profile
Integration Result
Integration Package / Adapter Execution
```

They remain external to the Core semantic authority.

Core continues to execute no ecosystem-specific adapter code in-process.

## Regression protection

v1.2.0 adds a selected Mission Snapshot golden signature that protects contract-significant envelope fields, boundary flags and representative serialization invariants without freezing every generated field.

The existing original-v1 Relationship Manifest golden remains fixed. Dedicated FDIR extension tests protect the additive relationship families.

The Integration Input Set is protected through behavioral tests for coherent single-operation production, failure-state representation, surface digests, deterministic set fingerprinting and manifest-last publication.

## Documentation and project readiness

Before publication, the complete active documentation set was audited against the v1.2 baseline.

The audit aligns:

```text
README and documentation landing page
Contributing and Security guidance
active Mission Model domain references
CLI and JSON compatibility references
generated-surface classification
scenario evidence classification
extensibility ownership
golden regression policy
Integration Framework maturity descriptions
```

Historical release notes and ADRs remain historical records and are not rewritten to imitate the current release.

## Migration

No Mission Model migration is required.

Consumers already supporting the previous Mission Snapshot and Integration Input Set wire identifiers require no wire-format migration for v1.2.0.

Consumers adopting the stable v1.2 Integration Input Set should validate the documented required surface identities and versions, verify the manifest digests and set fingerprint, and reject incompatible required surfaces rather than reparsing raw Mission Model YAML.

## Architectural boundary

OrbitFabric remains a Mission Data Contract framework.

v1.2.0 does not add:

```text
flight runtime behavior
ground runtime behavior
plugin execution inside Core
relationship or dependency graph execution
Studio-specific semantic authority
OpenOBSW/OpenSVF/YAMCS-specific Core semantics
CCSDS/PUS/CFDP implementation
```

The release strengthens the generic contract boundary without widening Core into the systems that consume it.
