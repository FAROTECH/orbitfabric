# OrbitFabric v1.3.0 - Adapter Management Foundation

Release date: 2026-09-04

## Summary

OrbitFabric v1.3.0 adds the first coherent Core-owned Adapter Management foundation while preserving the stable Mission Data Contract and the provider-neutral integration architecture.

The release introduces candidate lifecycle, desired-state, release-attachment and Catalog capabilities that let external OrbitFabric Integration Packages be installed, verified and tracked as exact releases without moving downstream-specific semantics or provider-specific acquisition into Core.

The release also adds the versioned operation-input v1 integration contract lane used by current external adapters.

The two relevant chains are now:

```text
Mission Model
    -> OrbitFabric Core
    -> coherent Core Integration Input Set
    -> Projection Profile
    -> external Integration Package / Adapter
```

and:

```text
Adapter Project Lock
    -> exact Adapter Catalog selection
    -> provider-specific Release Source outside Core
    -> ResolvedAdapterRelease
    -> Core Adapter Manager lifecycle
    -> Installed Adapter State
    -> verification / execution
```

Core owns exact identity, desired/actual state and lifecycle semantics. Provider-specific acquisition remains outside Core.

## Added capabilities

### Versioned operation-input integration contract lane

v1.3.0 adds the candidate operation-input lane for external Integration Packages:

```text
Integration Package Manifest 0.2-candidate
orbitfabric.adapter_cli.v1
Integration Result 0.2-candidate
```

The v1 lane keeps the coherent Core Integration Input Set and Projection Profile as common context and allows zero or one required file-backed operation input.

The first contract-defined operation role is:

```text
scenario
```

Core publishes JSON Schemas, positive and negative fixtures, conformance checking and a compatibility matrix for this lane.

This does not move target-specific scenario semantics into Core.

### Adapter Manager M0

The candidate Core-owned Adapter Manager lifecycle adds:

```text
orbitfabric adapter install
orbitfabric adapter list
orbitfabric adapter inspect
orbitfabric adapter verify
orbitfabric adapter execute
orbitfabric adapter remove
```

The first installation backend is:

```text
python-wheel-managed-env
```

It installs an exact wheel into a dedicated managed Python environment, discovers exactly one descriptor-owned `integration_package.json` from the installed distribution and binds execution through the installed environment.

Core maintains user-scoped Installed Adapter State and verifies release descriptor integrity, manifest integrity/conformance, execution binding and backend materialization.

### Adapter Project Lock M1

v1.3.0 adds the candidate Adapter Project Lock contract for project-scoped exact desired adapter state.

A lock entry records:

```text
Source Coordinate
exact release version
Release Descriptor SHA-256
artifact id
artifact SHA-256
installation backend id
```

It does not record machine-local instance ids, install paths, executable paths or mutable provider locators.

The Core CLI adds:

```text
orbitfabric adapter lock validate
orbitfabric adapter lock check
```

Lock comparison reports per-adapter `MATCH`, `MISSING` or `MISMATCH` and an overall project state of `MATCH` or `NOT_SATISFIED`.

### Explicit-source install from Project Lock

Core adds an explicit-source lane for installing one exact lock entry from already-available Release Descriptor and artifact bytes:

```text
orbitfabric adapter lock install
```

The lane verifies lock identity before backend materialization and converges on the same Core installation transaction used by direct installation.

An already satisfied entry produces an idempotent `MATCH -> NOOP` result.

A mismatching installed release is not implicitly removed; the exact locked release is installed side-by-side.

### Source-neutral resolved-release attachment seam

v1.3.0 promotes the provider-neutral handoff:

```text
provider-specific Release Source
    -> verified local descriptor/artifact bytes
    -> ResolvedAdapterRelease
    -> Core Project Lock install lifecycle
```

This lets remote or local Release Sources acquire exact release bytes without moving provider/network behavior into Core.

Project Lock identity remains independent from mutable provider URLs, cache locations or mirrors.

The release also keeps provider facts separate from Core trust/acceptance semantics.

### Provider-neutral Adapter Catalog exact selection

Core adds a candidate provider-neutral Adapter Catalog model with exact release selection.

Catalog identity is anchored by:

```text
Source Coordinate
+ exact release version
+ expected Release Descriptor SHA-256
```

Provider configuration and provider-owned release references remain opaque to Core.

Exact selection fails closed on missing or ambiguous adapter, release or source-binding identity.

The Core CLI adds local Catalog inspection commands:

```text
orbitfabric adapter catalog validate <catalog.json>
orbitfabric adapter catalog list <catalog.json>
orbitfabric adapter catalog select <catalog.json> <SOURCE_COORDINATE> --version <EXACT_VERSION>
```

These commands perform no network access and no provider dispatch.

## Supported provider-explicit consumer path

v1.3.0 intentionally does not introduce a unified Core command such as:

```text
orbitfabric adapter install <logical-adapter> --version <version>
```

Such a command would require Core to map provider identifiers to installed provider implementations. A generic provider registration/dispatch protocol remains deferred until additional materially different providers provide enough evidence to generalize safely.

The currently supported public path is therefore explicit:

```text
OrbitFabric Core
    local Catalog validation/listing/exact selection
    Project Lock and Adapter Manager lifecycle

provider-specific Release Source
    remote acquisition and verification
    ResolvedAdapterRelease handoff to Core
```

The first provider product is the separate GitHub Release Source repository:

```text
FAROTECH/orbitfabric-github-release-source
```

Its first packaged release depends on:

```text
orbitfabric>=1.3,<2
```

Core 1.3.0 therefore publishes the Core-owned boundary required by that product without importing GitHub-specific code.

## Compatibility impact

### Mission Data Contract

No semantic migration.

No Mission Model fields, domains, controlled values, identifier rules, reference meanings, lint diagnostic semantics or scenario expectation semantics are removed, renamed or redefined.

The stable v1.x Mission Data Contract remains unchanged.

### CLI

Additive candidate CLI surface.

v1.3.0 adds the `orbitfabric adapter` command family, its `lock` and `catalog` subcommands, and exact install/inspect/verify/execute/remove workflows.

Existing stable CLI workflows remain compatible.

Human-oriented CLI text remains non-normative unless explicitly documented otherwise.

### JSON reports and machine-readable contracts

Existing stable lint/simulation report semantics are unchanged.

v1.3.0 adds independently versioned candidate schemas and records for:

```text
Integration Package Manifest 0.2-candidate
Integration Result 0.2-candidate
Adapter Release Descriptor 0.1-candidate
Adapter Project Lock 0.1-candidate
Adapter Catalog 0.1-candidate
```

These additions do not modify the existing stable Mission Model or Core Integration Input Set semantics.

### Lint diagnostics

No stable lint diagnostic behavior change.

### Scenario evidence

No Core scenario YAML or scenario expectation semantic change.

The new operation-input integration lane can carry a scenario file to an external Integration Package, but downstream scenario projection remains adapter-owned.

### Generated runtime and ground artifacts

No stability promotion or semantic change.

Generated C++17 runtime-facing bindings and generic ground-facing artifacts remain reproducible contract artifacts, not flight software or a ground segment.

### Dependencies

`jsonschema` is now a base runtime dependency because integration, Adapter Release and Adapter Project Lock conformance are required by Adapter Manager lifecycle operations.

Python support remains:

```text
Python 3.11+
CI: Python 3.11 and 3.12
```

## Stability and maturity classification

OrbitFabric uses mixed maturity intentionally.

The package release is `1.3.0`, but the following new Adapter Management surfaces remain candidate:

```text
Adapter Manager lifecycle product surface
Adapter Release Descriptor 0.1-candidate
Adapter Project Lock 0.1-candidate
explicit-source install-from-lock lane
source-neutral Release Source attachment seam
Adapter Catalog 0.1-candidate
Adapter Catalog CLI
Integration operation-input v1 contract lane
```

Publishing Core 1.3.0 does not automatically promote those surfaces into the stable Mission Data Contract.

The stable v1.x Core Integration Input boundary introduced in v1.2.0 remains stable and unchanged.

## Architectural boundary

OrbitFabric Core remains provider-neutral and ecosystem-neutral.

v1.3.0 does not add:

```text
GitHub-specific acquisition inside Core
remote Catalog fetching inside Core
provider registration/dispatch protocol
latest/stable/range version solving
automatic adapter upgrades
project-wide automatic reconcile
non-Python installation backends
in-process ecosystem adapter loading
flight runtime behavior
ground runtime behavior
Studio-specific semantic authority
```

External Release Sources may perform provider-specific acquisition, but they must hand an exact verified `ResolvedAdapterRelease` into Core-owned lifecycle semantics.

## Reference-proven acceptance

The public F Prime adapter release `0.1.1` was used as an end-to-end acceptance fixture for the Catalog and Release Source path.

The accepted path demonstrated:

```text
Core Catalog validate/list/select
    -> provider-specific exact public release resolution
    -> Project Lock MISSING
    -> Core install INSTALLED
    -> Project Lock MATCH
    -> Core verify PASS
    -> acquisition bytes removed
    -> Core verify PASS
    -> Project Lock MATCH
    -> repeat ensure NOOP without Catalog/provider access
```

This proves consumer usability of the provider-explicit path without requiring a premature universal provider protocol.

## Migration

Existing OrbitFabric v1.2 missions require no Mission Model migration.

Existing stable Core-owned structured surfaces require no wire-format migration.

Users who do not use Adapter Management can upgrade without adopting Project Lock, Catalog or provider-source workflows.

Adapter-management consumers should treat the new contracts as candidate and pin exact versions/digests where reproducibility matters.

## Release boundary

v1.3.0 is a deliberate additive product release:

```text
stable Mission Data Contract preserved
stable Core Integration Input Set preserved
candidate operation-input contract added
candidate Adapter Management lifecycle added
candidate exact desired-state lock added
candidate provider-neutral Catalog selection added
provider-specific acquisition remains outside Core
```

The release strengthens the external adapter lifecycle without turning Core into a package registry, provider SDK, plugin host or downstream-specific runtime.
