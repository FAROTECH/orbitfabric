# v1.2 Integration Input Stability Decision

Status: **Accepted for v1.2.0**  
Scope: Mission Snapshot, Core Integration Input Set and additive FDIR Relationship Manifest families  
Release gate: #224  
Integration input design gate: #228

---

## Decision

OrbitFabric v1.2.0 promotes the Core-owned integration input boundary to a stable compatibility commitment without changing Mission Model semantics.

The release remains a consolidation release:

```text
Mission Model semantics                    unchanged
Mission Snapshot                           stable Core-owned surface
Core Integration Input Set                 stable Core-owned integration boundary
FDIR Relationship Manifest families        additive stable-compatible extension
Projection Profile contract                0.1-candidate extension contract
Integration Result contract                0.1-candidate extension contract
Integration Package / Adapter contract     0.1-candidate extension contract
```

The Mission Model remains the source of truth.

---

## Mission Snapshot stability

`mission_snapshot.json` is stable from v1.2.0 for its documented envelope, failure behavior, boundary semantics and contract role:

```text
What complete Mission Model did OrbitFabric Core actually load?
```

The format identifier remains:

```text
snapshot_version = 0.1-candidate
```

This is deliberate. Stability classification and format-version identifiers are separate OrbitFabric concepts. Changing a format identifier only to remove the word `candidate` would create avoidable incompatibility without changing semantics.

The stable commitment does not freeze the entire serialized `model` object byte-for-byte. `model` is a faithful JSON serialization of the loaded Mission Model and follows the Mission Model's own compatibility rules. Compatible consumers must tolerate additive Mission Model fields when the Mission Model contract permits them.

A selected golden signature protects contract-significant Snapshot fields and serialization invariants without freezing the complete generated JSON.

---

## Core Integration Input Set stability

The coherent Core Integration Input Set defined by #228 is stable from v1.2.0 as the supported Core-to-integration input boundary.

Its format identifier remains:

```text
input_set_version = 0.1-candidate
```

The stable commitment covers the documented semantics of:

- canonical surface roles and required/companion classification;
- explicit surface availability records;
- load and lint state separation;
- per-surface identity/version/digest records;
- RFC 8785/JCS-based input-set fingerprinting;
- one-load/one-lint coherence;
- manifest-last completeness;
- required-surface compatibility gating;
- no raw-YAML semantic fallback;
- Core diagnostic ownership.

The stable input boundary does not make Profile, Result or Adapter contracts Core-owned stable surfaces.

---

## FDIR Relationship Manifest classification

The seven post-v1.1 FDIR relationship families are admitted as additive stable-compatible Relationship Manifest families:

```text
autonomous_action_triggered_by_fault
autonomous_action_uses_command_source
fault_observes_telemetry
fault_recovery_dispatches_command
fault_recovery_targets_mode
recovery_intent_includes_command
recovery_intent_targets_mode
```

They are derived deterministically from explicit Mission Model fields. They do not rename, remove or redefine original v1 relationship families, infer graph semantics or create synthetic entities.

The original v1 Relationship Manifest golden signature remains unchanged so it continues to protect the original compatibility baseline. Dedicated FDIR regression tests protect the additive families.

Consumers must tolerate unknown additive relationship types according to the Relationship Manifest compatibility rule and must never guess unknown semantics.

---

## Compatibility and migration

No Mission Model migration is required for v1.2.0.

Existing consumers that already support:

```text
orbitfabric.mission_snapshot / 0.1-candidate
orbitfabric.integration_input_set / 0.1-candidate
```

continue to use the same wire identifiers.

Consumers that did not previously use these candidate surfaces may adopt them as stable v1.2 Core boundaries.

---

## Explicit non-goals

This decision does not introduce or stabilize:

- Projection Profile target-specific semantics inside Core;
- Integration Result as a Core Mission Data Contract surface;
- Integration Package execution inside Core;
- plugin discovery/loading/execution;
- Studio-specific APIs;
- relationship graph behavior;
- dependency graph behavior;
- runtime behavior;
- ground behavior;
- OpenOBSW/OpenSVF/YAMCS-specific Core semantics.
